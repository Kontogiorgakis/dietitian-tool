# Internationalization (next-intl)

- Locales are `en` and `el`. Routing config lives in `lib/i18n/routing.ts`, and middleware lives in **`proxy.ts`**, not `middleware.ts`.
- Every page and layout receives `params: Promise<{ locale: string }>`, so **always await it** (Next.js 16 requirement).
- Server components: call `setRequestLocale(locale)` first, then `await getTranslations()`. Client components use `useTranslations()`.
- Navigation goes through the helpers in `lib/i18n/navigation.ts` (`Link`, `redirect`, `useRouter`), never `next/link` or `next/navigation` directly in localized routes.
- Translation keys are type-safe via `global.d.ts`.
- The layout validates the locale with `hasLocale()` and returns `notFound()` for invalid ones, and `generateStaticParams()` pre-renders every locale.

## Adding or renaming a key

**A new or renamed key must be added to BOTH `messages/en.json` and `messages/el.json`, then the dev server MUST be restarted.** next-intl module-caches the locale JSON, so a `MISSING_MESSAGE` error for a key you just added is almost always the stale server, not a typo. `pnpm tsc --noEmit` passing proves nothing here, because types read the live JSON. Verify the key AND its namespace before debugging anything else:

```bash
node -e "console.log(require('./messages/en.json').Namespace.key)"
```

## Server/client split

A section that needs translations AND client state (lightbox, form, scroll listener) gets split in two: a server wrapper calls `getTranslations()` and renders a client child that uses `useTranslations()` plus `useState`. Example: `gallery-section.tsx` (server) renders `gallery-grid.tsx` (client). Never add `"use client"` to `page.tsx` or `layout.tsx` to solve this.
